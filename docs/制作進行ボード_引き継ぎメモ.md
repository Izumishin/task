## 1. これから作るもの（目的）

**毎週月曜に手作業でChatWorkへ貼っている「制作（DTP・編集）の進行一覧」を自動化する。**

現状：担当者が土日に自宅で生産表とChatWorkを突き合わせ、翌週分の一覧を手で作って月曜に投稿している。
この情報収集と清書をなくすことが目的。

**出力先はChatWorkでなくてよい。** 印刷進行ボードと同じように、
関係者がブラウザで見られる画面であればよい（機密性の感覚も印刷進行ボードと同じで、社内共有前提）。
ChatWorkには「今週の制作進行はこちら」とURLを貼るだけで運用できる。

### 印刷進行ボードとの関係

同じ案件（同じ受注番号）の**上流工程**にあたる。

```
制作（DTP・編集）        印刷進行ボード（既存）
入稿 → 初校 → 再校 → 三校 → 下版 → 印刷 → 外注 → 工務 → 納品
└──── これから作る範囲 ────┘  └──── 既にある範囲 ────┘
```

印刷進行ボードの仕様書では「電算編集室の工程（新組・初校・再校・念校・校了）の表示」を
意図的にスコープ外にしていた。その部分を別画面として作ることになる。

**重要：別システムにはしないこと。** 同じ生産表・同じ受注番号・同じGAS基盤を使う。
取込処理を二重に持つと、片方だけ壊れる／列マッピングがずれる事故が起きる。
同じリポジトリ（`Izumishin/task`）・同じスプレッドシート・**画面（とデータシート）だけ別**にする。

## 2. 現状のChatWork投稿の読み方

### 凡例（担当者からの回答・確定）

| 記号 | 意味 |
|---|---|
| ◆ | 入稿予定 |
| ⭐️ | 下版予定 |
| 🔹 | 入稿・進行中 |
| 🔸 | 下版 |
| 🏠 | 社内オフ |
| 🖨 | オンデ（オンデマンド） |
| 💿️ | データ納品（PDF） |

### 掲載対象（確定）

- **冊子のみ**。細かい端物は載せない
- 判定は **AI列「大分類」** を使う（値の例：冊子／端物）

### 投稿の構造

```
＊DTP
【和泉】                      ← 組版担当者ごとに見出し
 ◆ ⭐️4/30 🏠22288 老年精神医学雑誌４月号【崎原】
 🔹 ⭐️納期：3/31 🏠21751 東京藝術大学 研究紀要 第21集【深澤】
【髙橋】※日本眼科医会（事務局代行業【礒網】）   ← 見出しに注記が付くことがある
 ...
＊編集
【菅井】※日本眼科医会
 ...
```

1行の構成：`状態記号` + `日付（下版予定日 or 納期）` + `出力記号` + `受注番号` + `得意先 品名` + `【営業担当】`

## 3. 生産表の構造（ここが一番の資産）

スプレッドシートID：`1yW4WyORgmAAzy-Clh6kafRK598pyY-Ee3OScoDXL1-A`
**一番右のシートが最新の月**（`2026年8月` などの月別シート）。

| **AI** | **大分類**（冊子／端物）← 掲載対象の判定に使う |
| AJ | 中分類 |

**制作の工程データ（Z〜AG）はすでに全部そろっている。** 新たに入力してもらう必要はない。

### 担当者の判定（要注意・確定した仕様）

**E〜L列のセルが「黒く塗られている」人が、その案件の担当者。**

- 数値（分）が入っていても、黒塗りでなければ担当ではない
- つまり **セルの値ではなく背景色で判定する**
**黒塗りは「条件付き書式」であることが確認済み（2026年9月）。**
このため `range.getBackgrounds()` では判定できない（条件付き書式の結果ではなく素の背景色が返るため）。
代わりに次のどちらかで判定する。

1. **条件式そのものを再現する（推奨）**
   条件付き書式の規則を見て、同じ条件をコードで書く。
   例：規則が「空白ではない」なら、`値が入っている＝担当者` と判定でき、**背景色を読む必要がない**。
   E〜L列は担当者ごとの作業時間（分）が入る列なので、この単純な条件である可能性が高い。
   最初に必ず実物の規則を確認すること（該当セルを選択 → 表示形式 → 条件付き書式）。

2. **規則をGASから読む**
   `sheet.getConditionalFormatRules()` で規則の一覧が取れる。
   各規則の `getRanges()` で対象範囲、`getBooleanCondition()` の
   `getCriteriaType()` / `getCriteriaValues()` で条件が分かる。
   規則が複雑な場合や、将来変更される可能性がある場合はこちらで動的に読む。

**やってはいけないこと**：`getBackgrounds()` で黒を探す実装。動いているように見えて、
条件付き書式のセルでは常に「白」が返るため、担当者が1人も取れない。

## 4. 再利用できる既存の部品（`shinko-board/`）

`shinko-board/Code.gs` は、そのまま流用または参考にできる。特に：

| 機能 | 関数・仕組み | 流用価値 |
|---|---|---|
| 生産表の最新シート判定 | `latestProductionSheet_()` | 高（そのまま使える） |
| 列マッピングの外出し | `SRC_DEFAULT` / `SRC_PROP` / `colToIndex_()` | **高**。列名（`M`, `AG`）をスクリプトプロパティで変更できる |
| 差分取込 | `importFromProductionSheet()` | 高（構造をまねる） |
| 実データ最終行の判定 | `boardLastDataRow_()` | **必須**（後述の落とし穴対策） |
| 更新権限 | `EDITOR_PIN`（合言葉）／`EDITOR_EMAILS` | 高。Workspace無しでも運用できる |
| 書き込みの排他 | `LockService` | 必須 |
| 調査用 | `diagnoseImport()` | **高**。列マッピングがずれたとき、これが無いと原因が分からない |
| 復旧用 | `repairBoardSheet()` | 中 |
| 画面 | `Index.html`（ダーク/ライト、3カラム、カード、編集パネル、30秒自動更新） | 高。見た目を揃えられる |

既存の設計方針（そのまま踏襲を推奨）：

- **データはスプレッドシートに置く**（画面が使えなくてもシート直編集で業務が止まらない）
- **生産表には絶対に書き込まない**。書き込むのは専用シートのみ
- **日付はプレーンテキスト `yyyy/MM/dd`**（タイムゾーンずれ回避）。読み取りはDate型も許容
- **更新者は1人、他は閲覧専用**
- 自動判定に頼らず、判断が要るものは人が1クリックで選ぶ

## 5. 踏んだ落とし穴（同じ失敗をしないために）

1. **`insertCheckboxes()` は範囲内の全セルに FALSE を書き込む**
   → `getLastRow()` が1000行目まで伸び、取込の追記位置が1001行目からになる。
   シートの上の方が空に見えて「1件も取り込まれない」ように見えた。
   対策：チェックボックスは `newDataValidation().requireCheckbox()`（値を書かない）を使い、
   追記位置は `getLastRow()` ではなく**A列（主キー）の最終行**で判断する。

2. **仕様書の列と実物の列が違っていた**
   → 仕様書には「A=受注NO」とあったが、実物はM列。A列は「電算（済）」で全行同じ値だったため、
   1件しか取り込まれなかった。
   対策：**新しい仕様書には、実物の列構成（またはスクショ）を最初から入れる**。
   列指定は最初からスクリプトプロパティで変更可能にしておく。

3. **見出しが3行ある**（1行目=表題、2行目=工程見出し、3行目=項目名）
   → 「見出し1行」を前提にすると全部ずれる。`PRODUCTION_HEADER_ROWS` で設定可能にしてある。

4. **納期の見出しは2行目にある列がある**
   → 診断機能で見出しを表示するときは、1〜3行目すべて・シートの右端まで出さないと見つからない。

5. **モック（テスト）が本物と違う挙動だと、バグを見逃す**
   → `insertCheckboxes` を何もしないモックにしていたため 1. を検出できなかった。
   対策：`shinko-board/tests/logic_test.js` は本物の副作用を再現している。これを土台にする。

6. **コードを直しただけでは公開中の画面は変わらない**
   → 「デプロイ ▸ デプロイを管理 ▸ 鉛筆 ▸ 新バージョン」で再デプロイして初めて反映される。
   「新しいデプロイ」を選ぶとURLが増えてしまうので使わない。

7. **公開設定が「組織内」以外だと、閲覧者のメールアドレスが取得できない**
   → `Session.getActiveUser().getEmail()` が空になり、メールでの権限判定が機能しない。
   対策：合言葉方式（`EDITOR_PIN`）。公開設定に関係なく動く。

8. **GASの実行時間上限は6分**。取込は必ず差分のみにする。

## 6. まだ確認が必要なこと（新セッションで最初に潰す）

1. **DTPと編集の振り分け**
   投稿では ＊DTP=【和泉】【髙橋】【野澤】、＊編集=【菅井】【橋本】。
   E〜L列のどこまでがDTPで、どこからが編集か（鈴木・派遣・磯網の扱い）を確定する。

2. **状態記号（◆🔹⭐️🔸）の付け方**
   凡例は判明済み（◆入稿予定／🔹入稿・進行中／⭐️下版予定／🔸下版）。
   これを **Z列（入稿日）とAG列（下版日）に日付が入っているか／未来か過去か** から
   機械的に決められるか、実データで検証する。
   行頭の記号と日付前の⭐️が併用されている行があるので、両方の意味を確認する。

3. **出力記号（🏠🖨💿）の判定条件**
   S列「出力」（CTP／オンデマンド／PDF）とT列「刷り」から決まると推定。実データで確認する。

4. **黒塗りの条件付き書式の「条件式」**
   条件付き書式であることは確認済み。あとは条件の中身（おそらく「空白ではない」）を確認し、
   その条件をコードで再現する。3章を参照。

5. **日付の表示ルール**
   投稿には `4/30` と `納期：3/31` の2種類がある。
   下版予定日がある案件は下版日、無い案件は納期、という使い分けと推定。要確認。

6. **見出しの注記**（`【髙橋】※日本眼科医会（事務局代行業【礒網】）`）
   固定の注記か、案件ごとの情報か。生産表のどこかにあるのか、人の頭の中にあるのか。

7. **週の区切り**
   「今週」は月曜〜金曜でよいか（印刷進行ボードと同じ）。投稿は月曜朝。

## 7. 推奨する進め方

### 順番

1. **まず週次の一覧を出す画面（または自動生成）だけ作る**
   目的は「土日の情報収集をなくす」こと。日々の進行管理の画面より先に、
   月曜に貼っていた一覧が自動で出る状態を作れば目的の大半が片付く。
   このとき「生産表だけで本当に全部作れるか」が検証できる。
2. **そのうえで、必要なら日々の制作進行ボードに広げる**

### 作り方

- 同じスプレッドシートに `制作進行` シートを新規作成（生産表には書き込まない）
- 同じApps Scriptプロジェクトに追加するか、別プロジェクトにするかは規模で判断。
  ただし**列マッピングの定義は1か所にまとめる**こと
- 画面は `shinko-board/Index.html` の見た目を踏襲すると、利用者が学び直さずに済む
- 権限は `EDITOR_PIN` 方式、公開設定は「全員」で運用可能（印刷進行ボードと同じ）

### 新しい仕様書（md）に必ず書くこと

- 実物の列構成（この文書の3章をそのまま貼る）
- 掲載対象の条件（AI列＝冊子のみ）
- 記号の凡例（2章）
- **やらないこと**（スコープ外を明記する。印刷進行ボードではこれが効いた）
- 更新できる人を1人に絞る
