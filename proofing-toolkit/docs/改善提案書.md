# 紀要組版・赤字反映ワークフロー改善提案書

## 1. 現状の課題

紀要論文の校正で、著者から手書き赤字を大量に入れたスキャンPDFが戻ってくるケースがあり、以下の2工程に時間と労力がかかっている。

| 工程 | 現状 | 課題 |
|---|---|---|
| InDesignでの修正作業 | スキャンを目で追いながら1件ずつ手作業で修正 | 判読・該当箇所探し・入力をすべて人力で行っている |
| 反映確認作業 | 赤字原稿と再校を並べて**全件目視** | 修正件数と同じだけの照合が必要。見落としリスクも作業者が負う |

実物(2026年7月号・塚田論文初校、本文16頁)を分析したところ、赤字は**114件**あり(リスト化した結果)、内訳はおおむね次の通りだった。

- **単純なテキスト置換・挿入・削除**(数字修正、脱字補い、語句差し替え、索引語の追加など): 全体の6〜7割
- **長文の書き足し**(ページ下部余白に数行): 4〜5件
- **体裁指示**(「※ゴチに」「各段2行分にしてレイアウト均等」など): 数件
- **照会・疑問出し**(「ママ?」「ABC順か50音順か」など): 数件
- **判読困難・曖昧な指示**: 1〜2割

つまり大半は「機械的に直せる・機械的に確認できる」修正であり、ここが自動化の余地になる。

## 2. 提案する新ワークフロー

核となる考え方: **「赤字」を最初に構造化データ(修正指示リスト)に変換してしまい、以降の修正・確認・照会管理をすべてそのリスト起点で回す。**

```
[著者からの戻り]
  手書きスキャンPDF ──→ Claudeで読み取り ──┐
  Acrobatデジタル注釈 ─→ XFDF書き出し→変換 ─┴→ ★修正指示リスト(CSV/Excel)
                                                      │
              ┌───────────────────────┼───────────────┐
              ▼                       ▼               ▼
   (a) InDesign一括置換        (b) 手作業修正      (c) 著者への照会表
   スクリプトで単純置換を      体裁・長文挿入は    「ママ?」等の回答欄
   自動適用(結果ログ付き)    リストを見ながら    としてそのまま送れる
              │                       │
              └──────────┬────────────┘
                         ▼
                  修正後PDFを書き出し
                         │
              ┌──────────┴────────────┐
              ▼                       ▼
   (d) 反映チェックスクリプト   (e) 新旧PDF差分レポート
   リスト全件を自動突合         意図しない変化(組版事故)
   → OK / NG / 要目視           の検出
              │
              ▼
   NG・要目視の項目だけを目視確認 → 再校提出
```

### ステップ1: 赤字のリスト化(スキャン → 修正指示リスト)

- スキャンPDFをClaudeにアップロードし、`prompts/赤字読み取りプロンプト.md` を貼り付けて実行する。ページ・指示種別(置換/挿入/削除/体裁/照会)・修正前・修正後が入ったCSVが得られる。
- **判読できない箇所は「照会」としてフラグ**させる設計にしてある。読み間違えたまま直すのが最悪なので、AIに断定させない。
- 出来上がったリストは必ず一度スキャンと突き合わせてスポットチェックする(固有名詞・数字・文献情報を重点的に)。全部を手で転記するのに比べれば大幅に軽い。
- Acrobatのデジタル注釈でくる著者の分は、注釈をXFDFに書き出して `tools/xfdf_to_list.py` で同じリスト形式に変換する。**手書き派もデジタル派も以降は同じ工程**に乗る。

実演サンプル: `sample/修正指示リスト_サンプル_塚田論文初校.csv`(実物の初校から起こした114件)

### ステップ2: InDesign修正

- リストの「自動置換可 = Y」の行(単純置換・脱字補いなど、今回実物では114件中29件)は `tools/apply_corrections.jsx` で一括適用する。
  - **既定はプレビューモード**: 置換予定箇所の前後の文脈とページ番号をCSVに出力するだけで、ドキュメントには触れない。人間が全行確認してから実行モードで流す2段階運用。
  - ヒットが**ちょうど1件のときだけ**置換する安全設計。0件・複数件・短文字列・書式境界またぎ・ページ不一致は置換せず結果CSVに記録されるので、その行だけ手で直す(詳細は「4. 導入コストと注意点」参照)。
  - 誤置換を防ぐため、リスト側の「修正前」には前後の文脈を含めて誌面内で一意になる文字列を入れておく(AI読み取りプロンプトにもその指示を織り込み済み)。
- 体裁指示・長文挿入・位置が曖昧な挿入は従来通り手作業。ただしリストの「反映済」列にチェックを入れながら進めることで、進捗と漏れが見える化される。
- 同種の修正が繰り返される場合(用語の表記統一など)は、InDesignの検索置換(GREP)でまとめて処理できるかをリスト上で先に見分けられる。

### ステップ3: 反映確認の自動化(ここが最大の時短ポイント)

- 修正後のPDFを書き出し、`tools/verify_corrections.py`(ダブルクリック用: `反映チェック実行.bat`)にリストと一緒に渡す。
- 各項目について「修正後の文字列が該当ページ±1にあるか」「修正前の文字列が消えているか」を自動判定し、**OK / NG / 要目視**の色分きHTMLレポートを出力する。
- 全件目視 → **「NG」と「要目視」(体裁・照会など文字面で判定できないもの)だけの目視**に縮小される。今回の実物なら114件の照合のうち目視が必要な分はおよそ半分以下になり、しかも「どこを見ればよいか」がリストで特定済みの状態になる。
- 併せて `tools/pdf_text_diff.py`(`新旧PDF差分実行.bat`)で修正前後のPDF全文を比較し、「指示リストで説明できない差分」がないかを確認する。これは修正時のミスタッチや流し込みズレによる**組版事故の安全網**。
- レイアウト崩れ(行送り・図版位置など)の目視確認には、Acrobat Proの「ツール > ファイルを比較」も併用すると効率的。

## 3. 期待できる効果

| 工程 | Before | After |
|---|---|---|
| 赤字の解読・転記 | 都度、原稿を目で追う | AIがリスト化(数分)+スポットチェック |
| 単純置換の入力 | 全件手入力 | 約4分の1は一括適用、残りもリスト消し込みで迷わない |
| 反映確認 | 全件を原稿と突き合わせ目視 | 自動判定でOKを除外し、NG・要目視のみ確認 |
| 照会管理 | 原稿の余白やメールに散在 | リストの「照会」行がそのまま質問表になる |
| 見落としリスク | 作業者の集中力頼み | 「リスト化漏れ」以外は機械が検出。二重チェック構造 |

## 4. 導入コストと注意点

- **初期設定**: Pythonのインストール(1回、10分)とInDesignスクリプトの配置(1回、5分)。手順は `docs/README_使い方.md` 参照。
- **AI読み取りの限界**: 手書きの癖・かすれによる誤読はゼロにはならない。本ワークフローは (1) 曖昧なものはAIに「照会」としてフラグさせる、(2) 反映チェックで機械的に再検証する、の二段構えで誤読の影響を抑えているが、**リスト化直後のスポットチェックは省略しないこと**。
- **一括置換の誤置換リスクと多層防御**: 「関係のない箇所が置き換わる」事故は信用に直結するため、スクリプトは以下の6層で防御している。
  1. **完全一致検索のみ**(大小文字・全半角・かなを区別)。あいまい一致はしない
  2. **ヒットがちょうど1件のときだけ置換**。0件・複数件は触らず記録のみ
  3. **プレビューモードが既定**。置換予定箇所の前後の文脈+ページ番号をCSVに出し、人間が全行確認してから実行する2段階運用
  4. **短文字列ガード**: 検索文字列が4文字未満の行は自動置換しない
  5. **書式境界ガード**: ヒット箇所の途中で書式(斜体・ゴシック等)が変わる場合は、置換で書式が失われるため自動置換しない
  6. **ページ整合ガード+変更記録**: 指示のページとヒットページが離れていれば未置換で警告。実行時は「変更を記録」をONにでき、全変更をストーリーエディタでレビュー可能
  それでも残る理論上のリスク(読み取りミス由来の文字列が偶然別の1箇所に存在する等)は、③のプレビュー確認と、新旧PDF全文差分チェック(指示リストで説明できない差分の検出)が最終防衛線になる。
- **一括置換の限界**: InDesignの検索は改行やスタイル境界をまたぐ文字列にヒットしないことがある。「見つからない」「スキップ」判定の行は手作業に回す運用とする(スクリプトはその前提で安全側に倒してある)。
- **確認スクリプトの限界**: PDFのテキスト抽出はルビ・縦組・異体字で乱れることがある。判定はあくまで一次スクリーニングで、最終責任は「NG・要目視の目視確認」で担保する。
- **機密面**: 外部AIに原稿を渡すことになるため、勤務先・発注元のポリシーに沿った利用範囲を確認しておく(学習に使われない設定・プランの利用を推奨)。

## 5. 段階的な導入プラン

1. **今号**: サンプルリスト(作成済み)を使って、反映チェックスクリプトだけ試す(確認作業の時短をまず体感する)
2. **次号**: AI読み取り→リスト化→手修正→自動チェック、のフルフローを1論文で試行
3. **その後**: 一括置換スクリプトを投入。デジタル注釈の著者分もXFDF変換で同じリストに合流させ、全論文に展開
